GRC engineering pipeline

A 6-stage build that takes AWS infrastructure from deployed to audit-defensible. Each stage feeds the next, and every control claim links to evidence an assessor can verify without asking me for it. Built between July 30 and August 17, 2026, for the GRC Engineering Club pipeline challenge. All 6 stages are complete.

Read the case study Source on GitHub

Chain intact

Week 1 Compliant infrastructure as code

Terraform, AWS S3

Terraform provisions an S3 bucket and a segregated log bucket that enforce 5 NIST SP 800-53 Rev. 5 controls: server-side encryption by default (SC-28), public access blocked on all 4 vectors (AC-3), versioning and 4 mandatory tags through the provider default_tags block (CM-6), and access logging to the log bucket (AU-3, AU-6).

The proof is the Terraform plan captured as JSON, not screenshots. A Terraform output surfaces the encryption algorithm in effect, so the attestation can't drift from what it attests to.

Week 1 source

Week 2 Executable controls

Open Policy Agent, Rego

3 Rego policies read the Terraform plan and return a verdict on SC-28, AC-3, and CM-6, with 6 unit tests covering the compliant and the violating case for each. The policies match resources by declared reference rather than by name, because the bucket name doesn't exist yet at plan time.

What testing caught. The first run against real infrastructure surfaced 36 false positives from a control scoped too broadly. The CM-6 tag rule was checking resources that can't carry tags, and filtering on tags_all scoped it correctly.

Week 2 source

Week 3 A gate that blocks

GitHub Actions, Conftest 0.69.0

A GitHub Actions workflow runs the policies against the plan on every pull request and blocks the merge when a control fails. Conftest is pinned for reproducibility, the pipeline fails closed, and branch protection on main requires the check.

What testing caught. The first attempt at the blocked case passed the gate. The SC-28 rule confirmed an encryption resource existed without reading the algorithm it declared, so sse_algorithm = "none" got through. A second rule now checks the algorithm against an approved allowlist.

PR #1, passed and merged PR #2, blocked

Week 4 Evidence you can trust

Cosign, Sigstore keyless signing

The workflow bundles its evidence, writes a SHA-256 sidecar, and signs the archive with Cosign keyless signing. There's no stored private key. The Sigstore certificate binds the signature to this repository and workflow, and the event is recorded in a public transparency log outside my AWS account.

Design decision. Signing runs even when the gate fails, because a run that blocked a merge is the run whose record matters most. A tamper test that appends 1 byte to the 262-byte archive fails verification immediately.

Week 4 source

Week 5 Native monitoring controls

AWS CloudTrail

A multi-region CloudTrail writes to a private, encrypted bucket with log file validation on, producing signed hourly digest files (AU-2, AU-12, AU-10). Digests arrived from 17 regions within 20 minutes, and validate-logs returned 1/1 digest files valid. The bucket policy pins the CloudTrail service principal to this trail with an aws:SourceArn condition. Everything was torn down the same day.

Open item. RA-5 and SI-4 aren't implemented. Security Hub returns SubscriptionRequiredException on this account, so the gap is documented in the code rather than worked around.

Week 5 source

Week 6 Speak the auditor's language

OSCAL 1.2.1, compliance-trestle

An OSCAL component definition and profile, both validating clean against OSCAL 1.2.1. The profile selects 4 controls from the NIST SP 800-53 Rev. 5 catalog. Each implemented requirement names the Terraform resource that enforces it and links to the signed evidence bundle.

The traversal. I verified the chain the way an outside assessor would. I followed the evidence link from the OSCAL document, downloaded the bundle into a directory that had never held it, and confirmed both the hash and the signature.

Week 6 source

12 Python tools that automate compliance tasks I've done by hand for years. Built independently and tested against synthetic data. They're functional prototypes, not production systems.

  • Access reconciliation. Compares system accounts against an HR roster and flags access that should have been removed. Tested against a 505-record synthetic dataset with a known answer key, it identified all 25 planted exceptions: 20 terminated users and 5 orphaned service accounts.

  • Access expiration checker. Flags overdue and due-soon access reviews, recertifications, and vendor assessments, sorted by urgency.
    • 
          
  • Access log analyzer. Parses raw authentication logs and flags after-hours access, failed logins, and privileged activity.
    • 
          
  • Control testing sample generator. Draws a reproducible random sample with a fixed seed, so a reviewer can re-create and defend the exact selection.
    • 
          
  • Control library. Tracks a control inventory with owners and last-tested dates, and flags which controls are overdue for testing.
    • 
          
  • Continuous control monitor. Runs control checks from the command line or a scheduler and writes every run, with its exception count, to a timestamped log. The expiration check is complete and the access check is next.
    • 
          
  • Findings summary. Tallies a findings register by severity for an instant Critical, High, Medium, and Low breakdown.
    • 
          
  • Findings register analyzer. Calculates finding age and groups by owner to show who's carrying the most and whose are oldest.
    • 
          
  • Findings deduplicator. Normalizes finding descriptions and removes duplicates, which matters when registers are merged across sources or assessment cycles.

Quarterly UAR agent

            Source on GitHub
          

          

          
An agent that runs a quarterly user access review and packages the result as a signed evidence bundle. Deterministic Python tools produce every count. The model routes to the right tool and writes the narrative, and every figure in the narrative appears verbatim in a tool result recorded in the manifest.

          
The bundle holds the tool output, a manifest with SHA-256 hashes of every input file and tool result, the full conversation record, and a checksum file covering all of it. It's archived and signed with Cosign keyless, and verification fails on a 1-byte change. Prototype on synthetic data.

        


        

          

            
This site

            Source on GitHub
          

          

          
Deployed from a CloudFormation template: a private S3 bucket behind a CloudFront distribution with Origin Access Control, so nothing but CloudFront can read the bucket, and HTTPS enforced. GitHub Actions deploys every push to main. The commit activity on this page is read from GitHub's public API in your browser.

          
I reviewed the template before running it and logged 2 gaps against my own site: encryption isn't explicitly declared, and access logging isn't enabled. Neither breaks anything, since S3 encrypts by default, but a control that isn't declared is a control an assessor can't verify.
